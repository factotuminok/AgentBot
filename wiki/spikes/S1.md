# S1 — Routing omp's OAuth token refresh through the orchestrator

**Verdict: PASS.** omp 18.12.1 has a public option that replaces its OAuth refresh step: `AuthStorageOptions.refreshOAuthCredential`. A worker process opened its run-private auth store with that option, seeded it from a snapshot sent over IPC, and sent every refresh to the parent as a `credential-request`. Both `ModelRegistry.getApiKey` and a real `createAgentSession` turn then used the refreshed token. The workers made zero requests to the token endpoint. CRED-03 can be built as written. The fallback in architecture §11 item 4 is not needed.

Plan's "Pass when": *A session in a separate process uses a refreshed token obtained only through the callback.* Observed: workers A and B sent `Authorization: Bearer access-v2` to the model endpoint. Only the orchestrator ever held `access-v2`. The token endpoint recorded no request from A, B, D or E.

## Question

Can omp's auth store route token refresh through the orchestrator (CRED-03)? The worker's run-private store must never call the provider's token endpoint. When a token needs a refresh, it must call a callback (`credential-request` in production) and use the credential the callback returns.

## How omp refreshes (SDK read, 18.12.1)

Paths are relative to `node_modules/@oh-my-pi/`.

- Every OAuth refresh goes through `OAuthRefresher` (`pi-ai/src/auth/refresh.ts`). That covers key resolution in `CredentialSelector` (`pi-ai/src/auth/select.ts:1064-1094`, for built-in and custom providers alike), usage reports (`auth/usage.ts:229`), health checks (`auth/health.ts:343`), the 401 auth-recovery retry, and `oauth.refresh(id)`. `getOAuthApiKey` (`pi-ai/src/registry/oauth/index.ts:115-138`) refuses expired credentials and never refreshes.
- `OAuthRefresher.#requestOAuthCredentialRefresh` (`refresh.ts:565-593`) picks the refresh implementation in this order: `AuthStorageOptions.refreshOAuthCredential` > the store's `refreshOAuthCredential` hook > the provider's own refresh (`getOAuthProvider(id).refreshToken`, or `refreshOAuthToken` for built-in providers). The override is used only when the row has a `credentialId` (`refresh.ts:578`). Rows loaded from a SQLite store always have one.
- `AuthStorage` passes the option to the refresher (`pi-ai/src/auth-storage.ts:191-196`). `discoverAuthStorage(agentDir, { authStorageOptions })` passes it through as well (`pi-ai/src/auth-broker/discover.ts:483-489`, wrapped by `pi-coding-agent/src/session/auth-broker-config.ts:215` and `sdk.ts:1024`).
- omp uses the same seam for its own auth broker: `createBrokerAuthStorage` in `pi-coding-agent/src/cli/auth-broker-cli.ts:131-136`, and the store hook in `RemoteAuthCredentialStore.refreshOAuthCredential` (`pi-ai/src/auth-broker/remote-store.ts:1257`). There, refresh tokens never leave the broker and clients hold the sentinel `REMOTE_REFRESH_SENTINEL = "__remote__"`.
- `authStorage.credentials.snapshot()` (`pi-ai/src/auth/pool.ts:692-705`) exports every credential with its row id. Each OAuth refresh token is replaced by `"__remote__"`.
- `authStorage.oauth.refresh(id)` (`OAuthRefresher.refreshById`, `refresh.ts:631`) is single-flighted per credential id: concurrent callers share one token exchange. It always mints a new token (it refreshes a copy with `expires: 0`).
- omp gives a refresh 10 s to complete (`OAUTH_REFRESH_OPERATION_TIMEOUT_MS` / `DEFAULT_OAUTH_REFRESH_TIMEOUT_MS`, `refresh.ts:43-44`). The `credential-request` round trip, including the orchestrator's own provider refresh, must answer within that time.
- All of these are public exports of `@oh-my-pi/pi-coding-agent` (`src/session/auth-storage.ts` re-exports `AuthStorage`, `SqliteAuthCredentialStore`, `REMOTE_REFRESH_SENTINEL` and the `AuthStorageOptions` type from pi-ai).

## What was built

`spikes/s1/`. Run it with `bun spikes/s1/run.ts`.

- `run.ts` creates a temp sandbox and starts `parent.ts` with `HOME`, `TMPDIR` and `PI_CODING_AGENT_DIR` pointing into it, so nothing touches `~/.omp`. It deletes the sandbox afterwards.
- `fake-provider.ts` registers the provider `s1-fake-oauth` through `ModelRegistry.registerProvider`. The provider uses `api: "openai-completions"` against a local base URL, plus an `oauth.refreshToken` that POSTs to the local fake token endpoint with an `x-s1-role` header naming the caller.
- `parent.ts` stands in for the orchestrator:
  - It serves the instrumented fake endpoints. `/token` rotates refresh tokens like Anthropic does, so a reused refresh token gets `invalid_grant`. `/v1/chat/completions` accepts only the current access token and streams `pong`.
  - It opens the master store with `AuthStorage.create(<sandbox>/orchestrator/omp-agent/agent.db)`. The store holds one OAuth sign-in: `access-v1`, `refresh-v1`, expired 60 s earlier.
  - It sends `master.credentials.snapshot().credentials` to each worker over Bun IPC. The spec never touches disk.
  - It answers `credential-request` messages. If the sign-in no longer exists, it refuses with `revoked: …`. If its stored access token differs from the worker's and is fresh for more than 5 min, it returns that token. Otherwise it calls `master.oauth.refresh(id)`. Replies carry the access token and expiry, with `"__remote__"` in the refresh field.
- `child.ts` stands in for the worker's agent host:
  - It creates its run directory with `mkdtemp`, sets `PI_CODING_AGENT_DIR` to it, and only then imports the SDK.
  - It opens the store with `discoverAuthStorage(runDir, { authStorageOptions: { refreshOAuthCredential } })` and seeds it with `authStorage.credentials.set(provider, credentials[])`. It maps each local row id to the orchestrator's row id.
  - It calls `registry.getApiKey(model)` three times concurrently, then runs `createAgentSession({ authStorage, modelRegistry, model, … })` and `session.prompt("ping")`.
  - It wraps `globalThis.fetch` to log every outbound request.
  - It deletes the run directory when it finishes.

Runs:

| Run | Snapshot | Hook |
|---|---|---|
| A, B (concurrent) | expired `access-v1` | installed |
| E | `access-stale` with a future expiry, which the model endpoint rejects with 401 | installed |

What this shows:

- **(a) The worker calls the callback.** Within each worker, three concurrent key lookups produced one `credential-request`.
- **(b) The session uses the refreshed token.** A and B: `getApiKey` returned `access-v2`, and the `createAgentSession` turn sent `Bearer access-v2` and got `pong`. Each worker's stored row afterwards held `access-v2` with `refresh: "__remote__"`.
- **(c) Workers never hit the token endpoint.** Workers A, B, D and E made no token-endpoint requests. The only outbound request from A and B (fetch log) was `POST …/v1/chat/completions`.
- **The orchestrator refreshed once for two concurrent requests.** One token exchange (`refresh-v1` → `refresh-v2`), so the refresh-token chain stayed intact.
- **401 recovery goes through the hook.** E's fresh-looking token got a 401. omp's auth retry called the hook with `reason: "auth-recovery"`, the orchestrator answered with its newer token without refreshing, and the retry succeeded.
- **The instrumentation catches a direct refresh.** Without the hook, C posted to the token endpoint itself. Because it held only `"__remote__"`, the endpoint answered `invalid_grant`. omp then disabled the row in C's own store; the orchestrator's chain was untouched.
- **A refused request disables the worker's copy.** D's refusal message contained `revoked`, which omp's `isDefinitiveOAuthFailure` pattern matches, so omp disabled the row in D's store and `getApiKey` returned `undefined`.
- **Run directories:** every worker's run directory was created with mode `700` and was gone after the run.

## Phase 3 API

**Worker (agent host).** Change `openSessionRuntime` (DevForge `src/agent/session.ts:49-55`):

```ts
const authStorage = await discoverAuthStorage(agentDir, {
	authStorageOptions: {
		refreshOAuthCredential: (provider, credentialId, credential, signal, reason) =>
			/* credential-request {provider, credentialId: orchestratorIdOf(credentialId), access: credential.access, reason} */,
	},
});
await authStorage.credentials.set(provider, credentials); // per provider, from the run-spec snapshot
// map authStorage.credentials.list(provider)[i].id → snapshot[i].id (same order; verify access matches)
```

- Return `{ access, refresh: REMOTE_REFRESH_SENTINEL, expires, …identity fields }`. On refusal, throw an `Error` whose message contains `revoked` or `invalid_grant`, so omp disables the row instead of retrying it.
- Leave `refreshOAuthCredentialMints` unset.
- Always pass `authStorage` and `modelRegistry` to `createAgentSession`.
- Set `PI_CODING_AGENT_DIR` before omp is imported (S2 found the same).
- Don't set `auth.broker.url` / `OMP_AUTH_BROKER_URL` in workers. The override still wins over a broker store, but the store would no longer be the run-private SQLite file.

**Orchestrator.**

- **Snapshot:** use `authStorage.credentials.snapshot().credentials`. It is redacted (refresh tokens → `"__remote__"`) and carries row ids.
- **Answering a `credential-request`:**
  - If the row is gone, refuse (CRED-05).
  - If its stored access token differs from the worker's and is still fresh, return the stored token.
  - Otherwise call `authStorage.oauth.refresh(id)`. Concurrent requests for the same id share one exchange; the "differs and still fresh" check stops requests that arrive in sequence from minting again.
- **Pre-dispatch refresh (CRED-02):** call `authStorage.oauth.refresh(id)` for any row with `expires < now + 10 min`. This path was not exercised in the spike.

## Fragility

- The hook is a documented public option (`AuthStorageOptions`, re-exported by `@oh-my-pi/pi-coding-agent`). omp's own auth broker depends on it, so it is a maintained seam, not an internal. `credentials.set` / `list` / `snapshot` and `oauth.refresh` are public namespace APIs. The spike used no private or `#` members and no module patching.
- Changes in a future omp release that would break this:
  - the order in which `#requestOAuthCredentialRefresh` picks a refresh implementation;
  - the `credentialId !== undefined` guard;
  - a new refresh call site that bypasses `OAuthRefresher`.

  Phase 3 should port the spike into `test/integration` (fake provider, fake token endpoint, assertion that workers make zero token-endpoint requests) so an omp upgrade that changes this fails CI.
- **Leak paths that ignore the hook:** some omp code opens its own store with `discoverAuthStorage()` when it is not given one: `web/search/index.ts:357,420,447`, `task/executor.ts:4244` (only without a parent `modelRegistry`), and `stencil/credential.ts:20`. Such a store has no override. Two things limit the damage:
  - The run-spec snapshot carries only `"__remote__"`. As run C showed, a stray refresh can only fail with `invalid_grant` and disable the worker's copy; it cannot rotate the orchestrator's refresh token.
  - Sessions created with an explicit `authStorage` and `modelRegistry` pass them to subagents (`task/structured-subagent.ts:642-643`).

## Consequences for the plan

- Architecture §11 item 4 is resolved: build CRED-03 as written. The fallback (short-lived access tokens only) is not needed.
- Suggested wording changes in `architecture.md` (not applied; the spike's target files are only `spikes/s1/*` and this note):
  - **CRED-02:** "puts a snapshot of all sign-ins into the run spec" → "puts a snapshot of all sign-ins into the run spec, with refresh tokens replaced by omp's `__remote__` sentinel (`credentials.snapshot()`); refresh tokens never leave the orchestrator."
  - **CRED-03:** "refreshes once per provider at a time" → "refreshes once per sign-in at a time". omp single-flights per credential row, and each account has its own refresh-token chain.
  - **§3 message table (`credential-request`):** the payload should be the provider, the orchestrator's credential id, and the worker's current access token, not just the provider. The orchestrator answers with the access token and expiry, or a refusal (CRED-05).
  - **Worker timing:** the orchestrator must answer within omp's 10 s refresh timeout.
- S2 Required changes item 6 ("Stop the host from refreshing tokens itself") is answered by the Phase 3 API above.

## Not tested

- Built-in providers (Anthropic, Codex). They use the same `select.ts` path (`refresher.refresh` with a row id) and, without a hook, would refresh against the real provider. The spike used only the fake provider so that no real endpoint was called.
- Several accounts for one provider.
- Containers, and an orchestrator connection other than Bun IPC.
- The orchestrator's pre-dispatch refresh.
- A refresh that runs into the 10 s timeout.
