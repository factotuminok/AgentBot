# S6 — Launcher on the rootless Podman socket

**Verdict: PASS, with one change to STO-06.** A Bun launcher in a container, running as uid 10001, talks to the rootless libpod REST API on the bind-mounted user socket. It detects rootless, refuses a rootful socket, and creates workers with a Podman secret, the stack network, a tmpfs, a memory limit with no swap, the label `agentbot.role=worker`, auto-remove and no published ports. Each worker reached the stub orchestrator by service alias, read its token, exited and was removed. The reaper removed an exited labelled container. It left alone an unlabelled container and one labelled `agentbot.role=web`. REST worked throughout, so the `podman --remote` CLI fallback is not needed.

What changes the plan: **a rootless engine cannot enforce a per-container disk limit.** `storage_opts.size` and sized `local` volumes both need XFS project quotas, and a rootless engine can't set them (details in §Disk limits). The only engine-enforced, size-limited area is a tmpfs, and its pages are charged to the memory limit. A 20 GiB checkout under a 4 GiB memory limit is therefore not possible under Podman. §Consequences, item 5, proposes new wording for STO-06 and NFR-02.

Two settings are needed to reach the socket at all (§Socket): `--security-opt label=disable` (SELinux) and `--userns=keep-id:uid=10001,gid=10001` (socket ownership).

Plan's "Pass when": *A worker container starts, reaches a stub orchestrator on the network, and is removed when it exits.* Observed: yes, 3 runs with capacity 2 (§Observed output).

## Environment

- `podman-machine-default`, libkrun, Fedora CoreOS 44.20260913.3.2, SELinux **Enforcing**, cgroup v2, crun, netavark.
- **The machine is in rootful mode** (`podman machine inspect` shows `Rootful=true`; the default connection is `podman-machine-default-root` → `/run/podman/podman.sock`). The machine was left in that mode. The spike used the rootless engine of VM user `core` (uid 501) via connection `podman-machine-default` → `/run/user/501/podman/podman.sock`. Its `podman.socket` user unit was already `enabled` and `active`, and `core` has linger on, so nothing had to be enabled.
- Podman **6.1.4** (server and client). `Libpod-Api-Version: 6.1.4`, Docker compat `Api-Version: 1.44`.
- Rootless engine: graph driver overlay on xfs (`/var`, mounted `prjquota`). Delegated cgroup controllers: `cpu io memory pids`. idmap: container 0 → host 501, container 1..1000000 → host 100000..
- Spike image: `docker.io/oven/bun:1.3-alpine` (Bun 1.3.14). Only `fetch({ unix })` and `Bun.serve` are used, both also in Bun 1.4.2.

## What was built

`spikes/s6/`:
- `Containerfile`: one image, three entrypoints (`bun launcher.ts | stub.ts | worker.ts`), `USER 10001:10001`.
- `launcher.ts`: libpod client over the unix socket. At start: `GET /info` and the rootless check (LCH-01), then a reap. Every 2 s: `GET /internal/scale` with the scale token, count active labelled workers, create and start `min(pendingRuns, capacity) - active` workers (LCH-02). It reaps again at the end (LCH-03). It holds only the scale token; the worker token is referenced by secret name (LCH-04).
- `stub.ts`: stub orchestrator on `:8081`. `GET /internal/scale` (scale token) returns `{pendingRuns}`. `GET /hello` (worker token) decrements `pendingRuns`.
- `worker.ts`: reads `/run/secrets/worker_token`, calls `http://orchestrator:8081/hello`, prints its uid, `memory.max`, `memory.swap.max`, mounts, `df` and permissions. It sleeps 6 s so that the driver can inspect it, optionally fills `/work` with 768 MiB, and exits 0.
- `run.sh [none|tmpfs|storage-opt]`: starts a fresh stub (network alias `orchestrator`) and the launcher with the socket mounted. It inspects the first worker while it runs, follows its logs and records `podman events` for the label. Afterwards it lists what is left. Env: `S6_PENDING`, `S6_CAPACITY`, `S6_MEMORY`, `S6_DURATION_MS`.

## Socket: path and permissions

Host path: `$XDG_RUNTIME_DIR/podman/podman.sock` (`/run/user/501/podman/podman.sock` here). It is `srw-rw----` `core:core`, SELinux type `user_tmp_t`. It is mounted at `/run/podman/podman.sock`. Result of `GET /v5.0.0/libpod/_ping` from Bun inside a container:

| `podman run` options | uid in ctr | result |
|---|---|---|
| (none) | 10001 | `ls`: Permission denied. fetch: `FailedToOpenSocket` |
| `--user 0` | 0 | `ls`: Permission denied (SELinux) |
| `--security-opt label=disable` | 10001 | socket shows as `0:0`, connect fails (uid 10001 is host uid 100000+, not the owner) |
| `--user 0 --security-opt label=disable` | 0 | **200** |
| `--userns=keep-id:uid=10001,gid=10001 --security-opt label=disable` | 10001 | **200**, socket shows as `10001:10001` |
| `--userns=keep-id:uid=10001,gid=10001` | 10001 | Permission denied (SELinux) |
| keep-id + `label=type:container_runtime_t` or `label=type:spc_t` | 10001 | 200 (both run as `spc_t`, same as `label=disable`) |

- **SELinux**: a `container_t` process may not connect to a `user_tmp_t` socket owned by an `unconfined_t` daemon. `label=disable` runs the launcher as `spc_t`. That matches what the launcher is anyway: whoever holds the socket is the host user. Relabelling the socket (`:z`) was not tried. It would not survive socket re-creation and would change a host file's label.
- **Ownership**: in a rootless container only container uid 0 maps to the socket owner. `keep-id:uid=10001,gid=10001` maps the host user to uid 10001, so the launcher can run non-root, as architecture §7.1 requires ("No entrypoint runs as root").
- Any URL host works with Bun's `unix` option (`http://d/...`). `/v4.0.0`, `/v5.0.0` and `/v6.0.0` prefixes all returned 200 on Podman 6.1.4. Use `/v5.0.0/libpod` (Podman ≥ 4.6 per OPS-03 also accepts it [INFERENCE: tested only on 6.1.4]).

/run/user/501/podman/podman.sock {"host.security": {..., "rootless": true,  "selinuxEnabled": true}, "version": "6.1.4", "remoteSocket": {"path": "unix:///run/user/501/podman/podman.sock"}}
```

The spike launcher, run in the rootful engine with the rootful socket mounted:

```

A Docker Engine socket has no `/libpod/` routes [INFERENCE: no Docker here to test]. The launcher must treat any non-200 response, or a missing `host.security.rootless`, as "not rootless Podman" and refuse.

## libpod API calls for phase 8

All calls go to `unix:/run/podman/podman.sock`, base `http://d/v5.0.0/libpod`, with JSON bodies (`content-type: application/json`).

| Purpose | Call | Observed reply |
|---|---|---|
| health / reachability | `GET /_ping` | 200 `OK` |
| rootless check, version | `GET /info` → `host.security.rootless`, `version.Version`, `host.cgroupVersion`, `host.cgroupControllers` | 200 |
| active workers | `GET /containers/json?all=true&filters={"label":["agentbot.role=worker"],"status":["created","running","paused","stopping"]}` (URL-encoded) | 200, array of `{Id, Names, State, Labels, …}` |
| exited workers (reap) | same with `"status":["exited","stopped"]` | 200 |
| create | `POST /containers/create` + spec below | **201** `{"Id":"…","Warnings":[]}` |
| start | `POST /containers/{id}/start` | **204** |
| remove | `DELETE /containers/{id}?force=false&v=true` | 200 |

- Valid `status` filter values: `created running paused stopping stopped exited removing unknown`. **`dead` and `configured` give HTTP 500** (`unknown container state: dead`).
- Filter by label on the server, then check `Labels["agentbot.role"] === "worker"` again on each result before deleting (the spike does this).
- Reap only `exited`/`stopped`. Reaping `created` would race with a create that has not started yet.

Container create spec (as sent; phase 8 sets the image, command and sizes):

```json
{
  "name": "agentbot-worker-<uuid8>",
  "image": "<worker image>",
  "command": ["agentbot", "worker"],
  "user": "10001:10001",
  "labels": { "agentbot.role": "worker" },
  "remove": true,
  "netns": { "nsmode": "bridge" },
  "Networks": { "<stack network name>": {} },
  "portmappings": [],
  "publish_image_ports": false,
  "env": { "AGENTBOT_ORCHESTRATOR_URL": "http://orchestrator:8081" },
  "resource_limits": { "memory": { "limit": 4294967296, "swap": 4294967296 } },
  "mounts": [
    { "destination": "/run/agentbot", "type": "tmpfs", "source": "tmpfs",
      "options": ["rw", "nosuid", "nodev", "noexec", "size=64m", "mode=0700", "U"] }
  ],
  "secrets": [
    { "source": "agentbot_worker_token", "target": "worker_token", "uid": 10001, "gid": 10001, "mode": 256 }
  ]
}
```

- `Networks` is capitalised in the libpod spec. Without `netns: bridge`, rootless uses pasta, not the named network [INFERENCE: always sent both].
- `remove: true` is `--rm`. Inspect showed `AutoRemove=true`, and events showed `died` then `remove` within the same second.
- `swap` equal to `limit` means no swap: the worker read `memory.max=268435456` and `memory.swap.max=0`. Inspect showed `Memory=268435456 MemorySwap=268435456`.
- **tmpfs ownership: use `"U"`.** `uid=10001`/`gid=10001` in the options are rejected: 500 `unknown mount option "uid=10001"`. With `U`, inspect shows `/run/agentbot:rw,nosuid,nodev,noexec,size=64m,mode=0700,uid=10001,gid=10001,rprivate,tmpcopyup`, and in the container `drwx------ 10001 10001 /run/agentbot`.
- **Secret**: it must exist before the create (`scripts/init-secrets.sh`). The launcher only names it. The spec's `uid/gid/mode` take effect: `-r-------- 10001 10001 /run/secrets/worker_token`, 64 hex chars read. `mode` is decimal JSON (`256` = `0400`).
- No published ports: `Ports=map[] PortBindings=map[] PublishAll=false`, and `podman port` printed nothing.
- DNS: the worker reached the stub by its network alias (`--network-alias orchestrator`, the compose service name) and by its container name.

## Disk limits (STO-06) under rootless Podman

| Option | Result (rootless, overlay on xfs with `prjquota`) |
|---|---|
| `storage_opts: {"size":"512m"}` via REST | **create fails**, 500: `--storage-opt is supported only for overlay over xfs with 'pquota' mount option`. Local rootless CLI: `storage options overlay.size and overlay.inodes not supported. Filesystem does not support Project Quota: failed to mknod …/backingFsBlockDev.tmp: operation not permitted`. Setting XFS project quotas needs real root (mknod, quotactl). |
| `podman --remote run --storage-opt size=512m` (macOS client → VM) | **silently ignored**, rootless *and* rootful: `df /` showed 99.4G and an in-container `dd` wrote 768 MiB. The `podman --remote` fallback must not be relied on for limits. |
| `POST /volumes/create {"Options":{"o":"size=512m"}}` (local driver, xfs quota) | 500: `volume options size and inodes not supported. Filesystem does not support Project Quota` |
| `POST /volumes/create {"Options":{"type":"tmpfs","device":"tmpfs","o":"size=512m,uid=10001"}}` | 201. A named tmpfs: same limits as a tmpfs mount, plus a volume the launcher would have to delete |
| tmpfs mount `size=512m` at `/work`, memory 1 GiB | **enforced**: `dd: error writing '/work/fill': No space left on device … 536870912 bytes (512.0MB) copied`, worker exit 0 |
| tmpfs mount `size=512m` at `/work`, memory 256 MiB | **worker killed, exit 137**, while writing to the tmpfs (tmpfs pages are charged to the memory cgroup, and there is no swap) [INFERENCE: OOM kill; the container was auto-removed before `memory.events` could be read] |
| rootful, for reference (`podman run` as root inside the VM, `--storage-opt size=512m`) | enforced: `df /` = 512.0M, `dd` stopped at 511.9 MB. Caveat seen: `podman run --rm` then **could not remove the full container** (`mkdir …/merged.1: no space left on device`) until the file in the layer was deleted by hand. Rootful is ruled out by LCH-01 anyway. |

What a rootless host can do:
1. **tmpfs** with `size=`: hard and per-run, but it counts against the memory limit. Fine for run-local storage (64 MiB). Not possible for a 20 GiB checkout.
2. **Worker-enforced soft limit**: the worker measures its checkout (for example `du -sk` of `/work` every few seconds and after each tool call) and fails the run with "the run ran out of disk space" past `limits` (default 20 GiB). The real ceiling stays the host disk (or the filesystem holding the rootless graphroot). Kubernetes `emptyDir.sizeLimit` is also enforced by periodic kubelet measurement and eviction, so the two runtimes report the same way.
3. **Admin-provisioned quota**: a host admin can put the rootless graphroot on its own filesystem. This caps all workers together, not each run. Out of scope for the launcher.

## Consequences for the plan

1. **Compose, launcher service** (phase 8, OPS-03). The compose translation was not run in this spike [INFERENCE: these keys map to the flags tested]:
   ```yaml
   launcher:
     user: "10001:10001"
     userns_mode: "keep-id:uid=10001,gid=10001"
     security_opt: ["label=disable"]
     volumes: ["${XDG_RUNTIME_DIR}/podman/podman.sock:/run/podman/podman.sock"]
   ```
   Give the stack network a fixed `name:` in compose (compose otherwise prefixes it with the project) and pass it to the launcher as `AGENTBOT_WORKER_NETWORK`. Workers resolve `orchestrator` through the compose service alias on that network.
2. **Launcher client**: use `fetch(url, { unix })` against `/v5.0.0/libpod`, with the calls and spec above and zod parsing of `/info` and `/containers/json`. At start, refuse unless `/info` returns 200 with `host.security.rootless === true` (LCH-01). Status filters: only the valid states listed.
3. **tmpfs mounts use `U`** for ownership, never `uid=`/`gid=`.
4. **Memory**: `resource_limits.memory.limit = swap = AGENTBOT_WORKER_MEMORY`. tmpfs contents count against it. Keep the run-local tmpfs small, and remember it when reading AGT-17 OOM reports.
5. **STO-06 / NFR-02 need new wording for Podman.** Proposed: "Under Podman, the checkout limit is enforced by the worker. It measures the checkout's size periodically and fails the run with 'the run ran out of disk space' when it passes the limit. The host disk is the hard ceiling. Under Kubernetes, `emptyDir.sizeLimit` enforces it." Remove "a size-limited scratch area" from LCH-02, or reword it as "a scratch directory whose size the worker limits". Phase 4's "Disk limit and its reporting" then means the worker-side check in both runtimes. Kubernetes can still use `sizeLimit` as the backstop.
6. **Fallback not needed.** The `podman --remote` CLI also silently drops `--storage-opt`, so it would not help with item 5.
7. **Testing on other hosts**: implementation §6 asks for S6 on two distributions. This run was one (Fedora CoreOS in a podman machine, SELinux enforcing). On a host without SELinux, `label=disable` is a no-op [INFERENCE].
