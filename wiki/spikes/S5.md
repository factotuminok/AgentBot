# S5 — KEDA ScaledJob with metrics-api, bearer auth, `accurate`

**Verdict: PASS with one required tuning.** The §4.4 settings give exactly one pod per pending run, never exceed `maxReplicaCount`, and drop to zero pods. But when a worker takes longer than `pollingInterval` (5 s) to claim its run after its pod starts, KEDA starts extra pods on every poll until the claim lands (2 runs → 8 pods observed). Fix: `scalingStrategy.pendingPodConditions: ["Ready"]` plus a worker readiness probe that passes only after the worker has claimed a run. With that change the slow-start case gives 2 pods for 2 runs. No fallback to the `default` strategy is needed.

## Question

Does a KEDA `ScaledJob` with the `metrics-api` scaler, bearer auth through a `TriggerAuthentication`, and `strategy: accurate` behave as architecture §4.4 says? Pending 0 → 3 → 0 should give 3 Job pods and then none, and there should never be more pods than `maxReplicaCount`.

## Setup

- kind v0.30.0 (`.tools/kind`) with `KIND_EXPERIMENTAL_PROVIDER=podman`, node `kindest/node:v1.34.0`, cluster `agentbot-spike-s5`. The podman machine is already rootful (`podman machine inspect` → `Rootful: true`, default connection `podman-machine-default-root`), so kind worked as-is and no machine settings were changed.
- KEDA **2.21.0** from the release YAML (`kubectl apply --server-side -f keda-2.21.0.yaml`). Re-tested on **2.12.0**, the minimum in OPS-08.
- `spikes/s5/fake-scale.py`: the fake orchestrator. `GET /internal/scale` returns `{"pendingRuns":P,"runningRuns":R}` and needs `Authorization: Bearer <token>`. `POST /claim` decrements P and increments R, or returns 204 when nothing is pending. Admin endpoints set P. It runs as Deployment/Service `orchestrator:8081` (`spikes/s5/fake-orchestrator.yaml`).
- `spikes/s5/worker.py`: the simulated worker. It sleeps `STARTUP_SECONDS` (cold start), then polls `/claim` every 1 s for up to `CLAIM_TIMEOUT_SECONDS` (20). After a claim it touches `/tmp/claimed`, sleeps `WORK_SECONDS`, calls `/done` and exits 0. With nothing to claim it exits 0.
- `spikes/s5/scaledjob-baseline.yaml`: the ScaledJob exactly as in the §4.4 table. `spikes/s5/scaledjob.yaml`: the version with the fix, **to be used in phase 9**.
- `spikes/s5/watch.sh`: prints one line about every 2 s with the fake's state (`p` = pending, `r` = running counter, `claims`, `empty` = empty claim polls, `unauth` = 401s) and the worker Jobs and pod phases. Consecutive identical lines are collapsed below. Times are host local time.

Bearer auth: in all runs `unauth` stayed 0 while the fake rejected any request without the right bearer token, and `scale poll` lines appear every 5 s. So `authMode: bearer` with a `TriggerAuthentication` `secretTargetRef` parameter `token` works on 2.12 and 2.21.

Note: `r` includes runs claimed by hand with `curl` and never marked done. It is not a pod count.

Cause (KEDA source, `pkg/scaling/executor/scale_jobs.go`): `accurate` creates `maxScale − pendingJobCount` new Jobs. Without `pendingPodConditions`, a Job stops counting as pending as soon as its pod is `Running`. A pod that is running but has not claimed yet therefore counts neither in `pendingRuns` (its run is still unclaimed) nor as a pending Job, so every poll adds another pod for the same run. The real worker starts Bun, may download omp (A-6) and opens a WebSocket before it claims, so its start-up can easily exceed 5 s.

**5. Slow start (15 s), fixed YAML (`pendingPodConditions: ["Ready"]` + readiness probe `test -f /tmp/claimed`), max 10.** 2 pods for 2 runs:
```

20:19:35 {"p":2,...} jobs=2 pods: ContainerCreating=2
20:19:52 {"p":0,"r":3,"claims":16} jobs=2 pods: Running=2
20:20:21 {"p":0,...} jobs=2 pods: Completed=2
20:20:26 ...         jobs=0 pods: none
```

**6. Fixed YAML, max 4, startup 3 s, work 40 s: scenarios 1–3 again.** Same results as baseline: 3 runs gave 3 pods and then none; 6 runs gave 4 concurrent pods, then 2, then none; a claim between polls gave 1 extra pod, which exited after 20 s.

**7. Fixed YAML, an idle unclaimed pod takes a new run.** While the extra pod from scenario 3 was polling, pending was set to 1. That pod claimed the run within 1 s and **no new Job was created**, because the unready pod counts as a pending Job.

**8. TTL.** Same run as scenario 7, with `successfulJobsHistoryLimit` removed (KEDA default 100). The pod completed at 20:25:46 and the Job and pod were gone at 20:26:47, which matches `ttlSecondsAfterFinished: 60`.

**9. Near the cap, fixed YAML, startup 15 s, pending 2, max 3.** KEDA 2.21: 2 pods. KEDA **2.12: 3 pods**, one extra, which exited after the claim timeout.
```
2.12:
20:36:20 {"p":2,...} jobs=2 pods: Running=2
20:36:24 {"p":2,...} jobs=3 pods: ContainerCreating=1 Running=2
20:36:35 {"p":0,"r":5,"claims":32} jobs=3 pods: Running=3
```
The cause is that before KEDA 2.19 `accurate` used `if maxScale + runningJobCount > maxReplicaCount { return maxReplicaCount − runningJobCount }`, and that cap branch ignores pending Jobs. 2.19.0 changed the test to `maxScale + runningJobCount − pendingJobCount` (checked in the v2.12.0 … v2.21.0 sources). On 2.12, A+B with the fixed YAML (3 runs → 3 pods; 6 runs at max 4 → 4 concurrent, then 2) behaved as on 2.21.

## Consequences for phase 9 (Helm chart) and the worker

- Use `spikes/s5/scaledjob.yaml`, templated as follows:
  - `maxReplicaCount: {{ worker.maxReplicas }}`;
  - trigger `url: http://<orchestrator svc>:8081/internal/scale`, `format: json`, `valueLocation: pendingRuns`, `targetValue: "1"`, `authMode: bearer`;
  - `authenticationRef` points to a `TriggerAuthentication` with `secretTargetRef: [{parameter: token, name: <secret>, key: <key>}]`;
  - `pollingInterval: 5`, `minReplicaCount: 0`;
  - `scalingStrategy: {strategy: accurate, pendingPodConditions: ["Ready"]}`;
  - Job `backoffLimit: 0`, `ttlSecondsAfterFinished: 60`, `restartPolicy: Never`, `terminationGracePeriodSeconds: 60`.
- Leave `successfulJobsHistoryLimit` at its default so the TTL decides when Jobs are deleted. Setting it to 0 makes KEDA delete a successful Job at the next poll (about 4 s, scenario 1) instead of after 60 s.
- **The worker must have a readiness probe meaning "this worker has claimed a run".** For example, an exec probe `agentbot health --claimed` (or a marker file in the run-local `emptyDir`) with `periodSeconds: 1`, `failureThreshold: 1`. Readiness must not flip back to false during the run, including while waiting on a human answer. Once the container exits, Ready becomes false, and KEDA briefly counts a finished Job as pending until the Job is marked complete (seen in the operator log as `"Number of pending Jobs": 3` at completion). This can delay the next scale-up by at most one poll, which is harmless.
- The worker must exit 0 when there is nothing to claim within `AGENTBOT_WORKER_CLAIM_TIMEOUT`. With `backoffLimit: 0`, a non-zero exit would leave failed Jobs behind.
- Extra pods from a claim between polls, or from the pre-2.19 cap branch, never exceed `maxReplicaCount`. Each lives at most for the start-up time plus the claim timeout.

## Requirement text to change

- **architecture §4.4 table:** add a row: `scalingStrategy.pendingPodConditions` | `["Ready"]`, with the worker readiness probe passing only after it has claimed a run | a started pod that has not claimed yet counts as pending, so slow worker start-up does not add pods (S5). Also extend the `scalingStrategy.strategy` reason: "… which is the queue model `accurate` expects, together with `pendingPodConditions`".
- **architecture §4.4 sentence after the table:** change it to "KEDA can start an extra pod for a run claimed between two polls (and, on KEDA < 2.19, near `maxReplicaCount`); that pod finds nothing to claim and exits after the claim timeout."
- **architecture §7.3 (Helm table, ScaledJob row):** add "readiness probe = run claimed" next to the liveness probe.
- **OPS-08:** KEDA ≥ 2.12 works. Optionally recommend ≥ 2.19, where `accurate` no longer adds an extra pod near the cap. No change is required.
