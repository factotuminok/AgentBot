# S3 — Git over the internal API

**Verdict: PASS.** A Bun handler around `git upload-pack --stateless-rpc` serves smart HTTP (protocol v2 and v0, gzip request bodies). From a depth-1 checkout of a start commit fetched by sha, all five steps worked: fetch, commit, bundle, import and fast-forward push. A moved issue branch rejected the push. Checkpoint and restore (RUN-17, RUN-18) also worked, from a second shallow worker. The `git http-backend` fallback is not needed.

One finding changes the plan: **`uploadpack.hideRefs` hides refs from the advertisement only. It does not stop a worker from fetching the objects behind them.** With protocol v2, which git uses by default, upload-pack serves *any* object in the repo, whatever the `uploadpack.allow*InWant` settings. A worker that knows the sha of another run's unpushed result or checkpoint in the same mirror can fetch it. See §Consequences, item 1, for the proposed fix (run refs in a separate repo that borrows the mirror's objects). The spike tested that fix too.

Plan's "Pass when": *All five steps work from a shallow checkout, and a moved branch rejects the push.* Observed: 43/43 checks green with git 2.50.1 (Apple Git-155) and Bun 1.4.2, in about 4 s. The temp dir is removed afterwards.

## Question

Git over the internal API (architecture RUN-17 to RUN-20, WS-02, §4.5): a depth-1 fetch of one commit by sha through a Bun HTTP handler around `git upload-pack --stateless-rpc` (with `uploadpack.allowReachableSHA1InWant` and `uploadpack.hideRefs=refs/agentbot`), a bundle whose only prerequisite is that commit, and a fast-forward push from `refs/agentbot/runs/<id>`.

## What was built

`spikes/s3/run.ts` is one self-contained Bun script. Run it with `bun spikes/s3/run.ts`; `S3_KEEP=1` keeps the temp dir. Everything lives in `mkdtemp(<tmp>/agentbot-spike-s3-*)`. git is isolated from the host with `HOME=<tmp>/home`, `GIT_CONFIG_NOSYSTEM=1`, `GIT_CONFIG_GLOBAL=<empty file>` and `GIT_TERMINAL_PROMPT=0`, so no credential helper or user config is involved. The script is written so it can become the phase 4 integration test: each step is a `check(name, ok, detail)`, and the process exits 1 on any failure.

1. **Fake GitHub**: a bare repo `github/acme/widget.git`. It has `main` (4 commits) and `agentbot/issue-1-x` (one commit on `main~1`), seeded from a normal clone.
2. **Mirror**: `state/repos/acme__widget.git` from `git clone --mirror`, then re-configured (§Consequences, item 2) and fetched with `--prune`.
3. **Endpoint**: `Bun.serve` on 127.0.0.1 with routes `/internal/git/<owner>/<repo>.git/{info/refs,git-upload-pack,git-receive-pack}` and in-memory leases `sha256(token) → {runId, owner, repo}`.
4. **Run r1**: worker W1 checks out, commits twice, dirties the tree and makes a checkpoint, which the orchestrator imports. W1 is deleted. Worker W2 restores the checkpoint, commits the leftovers and bundles. The orchestrator imports the bundle and pushes it to `agentbot/issue-1-x`.
5. **Run r2**: W3 checks out the new issue head, commits and bundles. A "human" pushes to `agentbot/issue-1-x` meanwhile. The import works, then the push is rejected twice: before and after a mirror fetch.
6. **Wants matrix**: which shas the endpoint serves, by config, protocol and target.
7. **Strict variant**: a run's bundle imported into `acme__widget.runs.git` (alternates → mirror), refused by the endpoint, and pushed from there.
8. **Bundle check negatives, auth and scope, gzip.**

## Endpoint handler (for `src/orchestrator/git/`)

```
GET  /internal/git/<owner>/<repo>.git/info/refs?service=git-upload-pack
POST /internal/git/<owner>/<repo>.git/git-upload-pack
```

- **Routing**: regex `^/internal/git/([^/]+)/([^/]+)\.git/(info/refs|git-upload-pack|git-receive-pack)$`. Owner and repo must match `^[A-Za-z0-9_][A-Za-z0-9_.-]{0,99}$` (no leading dot, so no `..`). Repo dir: `<state>/repos/<owner>__<repo>.git`. Anything else returns 404, including dumb-HTTP paths like `/HEAD`.
- **Auth**: `Authorization: Bearer <lease>`. `Basic` with the lease as password (`x-access-token:<lease>`) is also accepted. Leases are looked up by `sha256(token)`, so raw tokens are never compared. Missing or unknown token → `401` with `WWW-Authenticate: Basic realm="agentbot"`; git then fails at once with `fatal: could not read Username …: terminal prompts disabled`. A valid lease for another repo → `403`; git prints `The requested URL returned error: 403`. Auth runs before any filesystem access.
- **Upload-pack only**: `git-receive-pack` in any form → 403. So does `info/refs` without `service=git-upload-pack`, which shuts out dumb HTTP. `git push` to the endpoint fails with `403` and the mirror is unchanged.
- **Config** is passed on upload-pack's argv. It holds no secret, and the mirror's config file stays clean:
  `git -c uploadpack.allowReachableSHA1InWant=true -c uploadpack.hideRefs=refs/agentbot upload-pack --stateless-rpc …`
- **Protocol**: if the `Git-Protocol` header matches `^[A-Za-z0-9=:._-]{1,256}$`, it is passed on as env `GIT_PROTOCOL`. Every git call in the run that didn't force `protocol.version` sent `Git-Protocol: version=2`.
- **`GET info/refs`**: `git upload-pack --stateless-rpc --http-backend-info-refs <dir>`, collected in full. For v0/v1 the body is prefixed with `001e# service=git-upload-pack\n` + `0000`; for v2 it is not (same as `git http-backend`). Headers: `Content-Type: application/x-git-upload-pack-advertisement`, `Cache-Control: no-cache`.
- **`POST git-upload-pack`**: requires `Content-Type: application/x-git-upload-pack-request` (else 415). With `Content-Encoding: gzip`/`x-gzip`, the body is piped through `DecompressionStream("gzip")`; any other encoding → 400. The body is read into memory with a cap of 16 MiB *after* decompression, then passed as `Bun.spawn(..., { stdin: body })` to `git upload-pack --stateless-rpc <dir>`. The response is upload-pack's stdout as a stream: `Content-Type: application/x-git-upload-pack-result`, `Cache-Control: no-cache`. Stderr and the exit code are logged when the process ends. A refused want reaches the client as git's own error (v2: `fatal: remote error: upload-pack: not our ref <sha>`).
- **Server**: `Bun.serve({ idleTimeout: 120, maxRequestBodySize: 16 MiB })`. The 120 s is an untested guess to cover pack generation on large repos.
- **gzip is real**: the depth-1 checkouts never gzipped, but a fetch from a repo with 200 unrelated local commits sent 3 of its 6 POSTs gzipped (`6 POSTs, gzip: false,false,true,true,true,false`), and they were decoded correctly.

Observed traffic over the whole run, as `method path status Git-Protocol gzip` (the 401/403/404 lines are the negative checks):

```
16× GET .git/info/refs 200 version=2 gzip=false
19× POST .git/git-upload-pack 200 version=2 gzip=false
 8× GET .git/info/refs 200 v0 gzip=false
 6× POST .git/git-upload-pack 200 v0 gzip=false
 4× POST .git/git-upload-pack 200 version=2 gzip=true
 1× GET .git/info/refs 403 version=2 | 3× … 403 v0 | 2× … 401 version=2 | 1× GET .git/HEAD 404 | 1× … 404 (traversal)
```

## Worker commands (RUN-17, RUN-18, RUN-19)

Env for every git command that talks to the endpoint. These variables are set per command only: never in argv, `.git/config` or the worker's global env (WS-02):

```
GIT_TERMINAL_PROMPT=0
GIT_CONFIG_COUNT=1
GIT_CONFIG_KEY_0=http.<orchestrator-base>/internal/git/.extraHeader
GIT_CONFIG_VALUE_0=Authorization: Bearer <leaseToken>
```

Scoping the key to the URL prefix means git sends the header to the endpoint only. After the checkout, `.git/config` and `FETCH_HEAD` contain neither the token nor `extraHeader` (checked).

**Checkout:**
```
git init -q
git config user.name <bot name>; git config user.email <bot email>
git fetch -q --depth=1 --no-tags <endpoint>/<owner>/<repo>.git <startSha>     # with the env above
git checkout -q -b agentbot/run-<runId> <startSha>
```
Result: `rev-parse --is-shallow-repository` = `true`, `rev-list --count HEAD` = 1, `.git/shallow` = the start sha, and `git log --oneline` shows only the start commit. The fetch was one `GET info/refs` + one `POST git-upload-pack`, both v2.

**Checkpoint** (one commit on top of HEAD holding the whole working tree, built in a throwaway index; the real index and working tree are untouched):
```
GIT_INDEX_FILE=.git/agentbot-checkpoint.index git read-tree HEAD
GIT_INDEX_FILE=.git/agentbot-checkpoint.index git add -A
tree=$(GIT_INDEX_FILE=.git/agentbot-checkpoint.index git write-tree)
cp=$(git commit-tree $tree -p HEAD -m "AgentBot checkpoint")
git update-ref refs/agentbot/checkpoint $cp
git bundle create -q checkpoint.bundle <startSha>..refs/agentbot/checkpoint
rm .git/agentbot-checkpoint.index
```
Observed: the status before and after was the same (` M README.md | A  notes/todo.txt | ?? scratch.txt`). The checkpoint tree held `scratch.txt` and `notes/todo.txt` but not the ignored `debug.log`. Bundle header: `{"version":2,"prerequisites":["<start>"],"heads":[{"ref":"refs/agentbot/checkpoint"}]}`. `git bundle create` needs a ref for the head, so a bare sha won't do; that is what `update-ref` is for.

**Restore** on a new worker, after the checkout above:
```
git fetch -q --no-tags checkpoint.bundle refs/agentbot/checkpoints/<runId>   # bundle as served by the orchestrator
git checkout -q -B agentbot/run-<runId> FETCH_HEAD
git reset -q --mixed HEAD~1
```
Observed: HEAD = W1's last run commit, both run commits are in `git log`, and the repo is still shallow. Status: ` M README.md`, `?? notes/todo.txt`, `?? scratch.txt`. A file that was *staged* comes back *untracked*, as expected from a mixed reset, and the ignored file is not restored.

**Result:**
```
git add -A && git commit -q -m "AgentBot: remaining changes for #1"     # only if there are changes
git rev-list --count <startSha>..agentbot/run-<runId>                   # 0 → report "no commits", don't bundle
git bundle create -q result.bundle <startSha>..agentbot/run-<runId>
```
The bundle was created in the shallow repo without trouble. `git bundle verify` in W2: `The bundle contains this ref: <sha> refs/heads/agentbot/run-r1 | The bundle requires this ref: <start> | … is okay`. `list-heads`: `<sha> refs/heads/agentbot/run-r1`. With no commits, `git bundle create` exits 128 with `fatal: Refusing to create empty bundle.`

## Orchestrator commands (RUN-19, RUN-20)

1. **Check the header** without git: the first line is `# v2 git bundle` or `# v3 git bundle`; `@…` lines are v3 capabilities; `-<sha>[ comment]` lines are prerequisites; `<sha> <ref>` lines are heads; a blank line ends the header. Require exactly one prerequisite, equal to the start sha, and the head `refs/heads/agentbot/run-<runId>`. Then `git -C <repo> bundle verify -q result.bundle`.
2. **Import** (forced: the ref belongs to the run, and checkpoints replace each other, so they are not fast-forwards):
   `git -C <repo> fetch -q --no-tags --no-write-fetch-head result.bundle +refs/heads/agentbot/run-<runId>:refs/agentbot/runs/<runId>`
   then `git rev-list --count <start>..refs/agentbot/runs/<runId>` (here 3 for r1).
   Checkpoints are imported the same way: `+refs/agentbot/checkpoint:refs/agentbot/checkpoints/<runId>`. The checkpoint is served back as `git bundle create - <start>..refs/agentbot/checkpoints/<runId>`.
3. **Push**, fast-forward only. No `+`, no `--force`. The target is the URL; for GitHub the token goes in `http.https://github.com/.extraheader`, as in DevForge:
   `git -C <repo> push --porcelain <url> refs/agentbot/runs/<runId>:refs/heads/agentbot/issue-<n>-<slug>`
   - Success: ` 	refs/agentbot/runs/r1:refs/heads/agentbot/issue-1-x	257f04f..b3143b8` (exit 0); creating a branch prints `*	… [new branch]`.
   - Branch moved and the new head not in the mirror: `!	refs/agentbot/runs/r2:refs/heads/agentbot/issue-1-x	[rejected] (fetch first)`, exit 1.
   - Branch moved and the mirror already fetched: `!	… [rejected] (non-fast-forward)`, exit 1.
   - Both mean "The branch changed on GitHub during this run". Match `^!\t` lines with `[rejected]` in the porcelain stdout. The GitHub branch stayed at the human's commit.
4. **Cleanup**: `git update-ref -d refs/agentbot/runs/<runId>` after the push or discard; `git update-ref -d refs/agentbot/checkpoints/<runId>` when the run finishes.

**Bundle check negatives**: a bundle built as `HEAD~1..agentbot/run-r3` has prerequisite `HEAD~1` ≠ start → rejected. If the agent amends the start commit, git makes a **root commit**, because the shallow graft hides the start's parents. The bundle then has `prerequisites []` → rejected. A plain bundle prerequisite check catches both.

## Wants matrix (observed, git 2.50.1)

The script pins this matrix, so a git upgrade that changes it fails the test. Targets: `main~1` (a non-tip commit reachable from `main`), the head of the hidden `refs/agentbot/runs/r2`, and a dangling commit that no ref reaches. "served" means a depth-1 fetch of that sha succeeded.

| endpoint config | protocol | non-tip | hidden-only | dangling |
|---|---|---|---|---|
| `allowReachableSHA1InWant` + `hideRefs` | v0 | served | **served** | refused (`not our ref`) |
| `allowReachableSHA1InWant` + `hideRefs` | v2 | served | **served** | **served** |
| `hideRefs` only (control) | v0 | refused¹ | refused¹ | refused¹ |
| `hideRefs` only (control) | v2 | served | served | served |

¹ Refused by the *client*: `error: Server does not allow request for unadvertised object <sha>`. The request never reaches upload-pack.

`ls-remote` (v0 and v2) and a hand-made v2 `ls-refs` never listed `refs/agentbot/*`; they listed `HEAD`, `refs/heads/main` and `refs/heads/agentbot/issue-1-x`. So hideRefs works for the listing, but it is not an access control. With v0, `allowReachableSHA1InWant` counts hidden refs as reachable on purpose. With v2, upload-pack does not check wants against refs at all. `allowReachableSHA1InWant` is still needed: with v0 the client refuses unadvertised shas without it, and the start commit may no longer be a tip by the time the worker fetches it.

**Strict variant, tested:** `state/repos/acme__widget.runs.git` was made with `git init --bare` and `objects/info/alternates` = `<mirror>/objects`. A run's bundle was imported there with the same commands. The object was absent from the mirror (`cat-file -e` fails), and the endpoint refused it on both protocols (v2: `fatal: remote error: upload-pack: not our ref <sha>`). `git push --porcelain <github> refs/agentbot/runs/r5:refs/heads/agentbot/issue-2-y` from the runs repo then created the branch.

## Consequences for the plan

1. **Isolation of unpushed run work (decision needed, recommended fix tested).** As written, temp refs live in the mirror behind `hideRefs`. A worker holding a lease for repo X can then fetch any other run's result or checkpoint of repo X by sha, and any dangling object too. The shas are unguessable and appear nowhere a worker can read, so the risk is low, but A-3 ("runs cannot see each other's code") holds only "by unknown sha". Recommendation: keep `refs/agentbot/runs/*` and `refs/agentbot/checkpoints/*` in a per-repo **runs repo** `<state>/repos/<owner>__<repo>.runs.git` that borrows the mirror's objects through `objects/info/alternates`. Bundle import, the checkpoint serve-back and the push all run in the runs repo, and the endpoint serves only the mirror. Run objects enter the mirror only after they are pushed to GitHub. Keep `hideRefs=refs/agentbot` as defence in depth. Text to change: RUN-17 (replace "MUST hide `refs/agentbot/*`" with "MUST serve only the mirror; temporary refs live in the runs repo"), RUN-18 and RUN-19 ("as `refs/agentbot/…` in the mirror" → "in the runs repo"), RUN-20, WS-07, WS-08, and the §4.6 diagram. Caveat [INFERENCE, not exercised]: the runs repo depends on mirror objects, so a mirror `gc` could prune a start commit that GitHub dropped (force push, or a squash-merged branch auto-deleted) while a run kept for Retry still needs it. Set `gc.pruneExpire=never` on mirrors (cheap), or run no `gc --prune` on a mirror whose runs repo has refs.
2. **Mirror refspec (WS-01, WS-07).** `git clone --mirror` sets `remote.origin.fetch=+refs/*:refs/*` and `remote.origin.mirror=true`. With that refspec, `fetch --prune` **deleted** `refs/agentbot/runs/probe` (observed). Phase 4 must configure the mirror like this:
   ```
   git clone --mirror <url> <state>/repos/<owner>__<repo>.git     # or clone --bare
   git config --unset remote.origin.mirror
   git config --replace-all remote.origin.fetch '+refs/heads/*:refs/heads/*'
   git config --add remote.origin.fetch '+refs/tags/*:refs/tags/*'
   ```
   With these refspecs, `fetch --prune` kept `refs/agentbot/*` (observed twice, including `runs/r2` during the moved-branch check). The refspec also stops `refs/pull/*` from being mirrored. With the runs repo (item 1) the mirror has no temp refs, but the narrowed refspec is still right. Push to an explicit URL, never to the remote name `origin` [INFERENCE: with `remote.origin.mirror=true`, git rejects refspecs on `push origin`; not exercised, since the script unsets it and pushes to the URL]. DevForge's layout (`clone --bare` + `+refs/heads/*:refs/remotes/origin/*`) would leave the clone-time `refs/heads/*` stale in the advertisement [INFERENCE], so don't port it unchanged.
3. **No commits (JOB-19, RUN-19).** git refuses to create an empty bundle. The worker must check `git rev-list --count <start>..agentbot/run-<id>` and report "no commits" in place of a bundle. The orchestrator turns that into "Agent produced no commits" (implement) or "no code changes needed" (revise, fix_ci). RUN-19 step 1 should say "upload a bundle, or report that the branch has no new commits".
4. **History rewrites.** Amending the start commit (observed) produces a bundle with no prerequisite, and RUN-19's check rejects it; any other rewrite of the start commit would give a missing or wrong prerequisite too [INFERENCE]. The prompt note about missing history (RUN-17) should also tell the agent not to amend or rebase the start commit. The failure message should say so, e.g. "the run rewrote the start commit".
5. **Imports are forced** into run-private refs (`+src:refs/agentbot/…`); only the push to GitHub is fast-forward only. RUN-19's "fast-forward only" applies to the push alone.
6. **Restore detail (RUN-17).** After restore, staged files become untracked. That is fine for the agent (it inspects `git status`), but the restart note should not promise "staged" state.
7. **Protocol and gzip support are required, not optional.** git defaults to v2 and gzips larger negotiation requests. The handler above covers both; no `git http-backend` fallback is needed.
8. **Tests**: the integration test must isolate git as the script does (`HOME`, `GIT_CONFIG_NOSYSTEM=1`, `GIT_CONFIG_GLOBAL`, `GIT_TERMINAL_PROMPT=0`), so that a developer's credential helper or user config can't answer the endpoint's 401 or change the protocol [INFERENCE: not tested without isolation].
